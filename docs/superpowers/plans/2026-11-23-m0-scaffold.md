**Goal:** A buildable, linted, CI-checked Go module whose `regreen` binary prints help and its version, plus the README stub, architecture doc, and decisions log.

func TestResolveVersion(t *testing.T) {
	info := func(v string, ok bool) func() (*debug.BuildInfo, bool) {
		return func() (*debug.BuildInfo, bool) {
			if !ok {
				return nil, false
			}
			return &debug.BuildInfo{Main: debug.Module{Version: v}}, true

		name    string
		ldflags string
		read    func() (*debug.BuildInfo, bool)
		want    string

		{name: "falls back to module version from go install", ldflags: "dev", read: info("v0.4.0", true), want: "v0.4.0"},

			if got := resolveVersion(tt.ldflags, tt.read); got != tt.want {

`cmd/regreen/version.go`:

```go
package main

import "runtime/debug"

// devVersion is the placeholder reported by builds that carry no version.
const devVersion = "dev"

// version is set at release build time with:
//
//	go build -ldflags "-X main.version=v1.2.3" ./cmd/regreen
var version = devVersion

// resolveVersion picks the version to report. A value injected with ldflags
// wins. Otherwise it uses the module version that the Go toolchain embeds
// when the binary is built with "go install module@version". Local builds
// have neither and report "dev".
//
// readBuildInfo is a parameter (in production: debug.ReadBuildInfo) so tests
// can supply fake build information.
func resolveVersion(ldflags string, readBuildInfo func() (*debug.BuildInfo, bool)) string {
	if ldflags != devVersion {
		return ldflags
	}
	if info, ok := readBuildInfo(); ok {
		if v := info.Main.Version; v != "" && v != "(devel)" {
			return v
		}
	}
	return devVersion
}
```

`cmd/regreen/app.go`:

```go
package main

import (
	"fmt"
	"io"
	"runtime/debug"
)

// Exit codes returned by run.
const (
	exitOK    = 0
	exitError = 1
	exitUsage = 2
)

const usage = `regreen hands mechanical CI failures to your own coding agent
and validates the fix against strict rules before anything is pushed.

Usage:
  regreen <command> [arguments]

Commands:
  mcp       Run the MCP server over stdio for a coding agent
  verify    Check a pushed change against the repository policy (for CI)
  init      Set up regreen.yml, the pre-push hook, and agent permission hints
  watch     Watch CI for manually pushed commits
  version   Print the regreen version
  help      Show this help

Flags:
  -h, --help   Show this help
  --version    Print the regreen version
`

// plannedCommands maps each command that is designed but not built yet to
// the milestone that delivers it. Entries move out of this map as the
// milestones land.
var plannedCommands = map[string]string{
	"mcp":    "M3",
	"verify": "M4",
	"init":   "M4",
	"watch":  "M6",
}

// run executes the CLI and returns the process exit code. It takes its
// arguments and output streams as parameters instead of reading os.Args and
// os.Stdout directly, so tests can call it in-process. Requested output goes
// to stdout; every diagnostic goes to stderr, because "regreen mcp" will
// reserve stdout for the MCP protocol.
func run(args []string, stdout, stderr io.Writer) int {
	if len(args) == 0 {
		fmt.Fprint(stderr, usage)
		return exitUsage
	}
	switch cmd := args[0]; cmd {
	case "help", "-h", "--help":
		fmt.Fprint(stdout, usage)
		return exitOK
	case "version", "--version":
		fmt.Fprintf(stdout, "regreen %s\n", resolveVersion(version, debug.ReadBuildInfo))
		return exitOK
	default:
		if milestone, ok := plannedCommands[cmd]; ok {
			fmt.Fprintf(stderr, "regreen %s: not implemented yet (planned for milestone %s)\n", cmd, milestone)
			return exitError
		}
		fmt.Fprintf(stderr, "regreen: unknown command %q\nRun 'regreen help' for usage.\n", cmd)
		return exitUsage
	}
}
```

# regreen-ci

regreen-ci hands mechanical CI failures (lint, formatting, type errors) to your own coding agent on your own machine, and validates the fix against strict rules before anything is pushed. The CLI binary is named `regreen`.

A failing CI is CI doing its job. regreen does not try to make the pipeline green at any cost. It removes the wasted human time on failures that need no human judgment, without weakening the checks.

## Status

Early development. Milestone M0 (scaffold) is complete: the binary builds and prints help and its version. Nothing else works yet.

| Milestone | Delivers | State |
|---|---|---|
| M0 | Scaffold: module, CLI skeleton, lint, CI, docs | done |
| M1 | Config loading and the policy engine | planned |
| M2 | GitHub Actions adapter and the failure model | planned |
| M3 | MCP server (`regreen mcp`) | planned |
| M4 | Enforcement: `regreen verify`, `regreen init`, pre-push hook | planned |
| M5 | Presets: JavaScript/TypeScript, Laravel, Flutter | planned |
| M6 | Watcher (`regreen watch`) | planned |

## Principles

- **Never trust the agent.** The only truth is the git diff and the result of re-running the check.
- **Deterministic first, agent second.** If the project's own autofix command resolves the failure, no agent is involved.
- **Language-agnostic core.** Projects declare check and fix commands in config. Languages are supported through presets, not Go code.
- **The final guarantee lives where the agent cannot edit it:** a CI check plus branch protection.
- **A human approves what reaches the main branch.** regreen never merges.

These controls guarantee that a fix follows the rules, not that it is logically correct. Human review before merge is part of the design.

# Architecture

regreen is one binary with several subcommands over one shared core. This document describes the intended layout and marks what exists today. It is updated at the end of every milestone.

## What exists today (M0)

```
cmd/regreen/
  main.go      main(): passes os.Args, os.Stdout, os.Stderr to run
  app.go       run(): command dispatch, usage text, exit codes
  version.go   resolveVersion(): ldflags value, then Go build info, then "dev"
```

A plain `go build` inside a git checkout reports a pseudo-version such as `v0.0.0-<date>-<commit>+dirty`, because the Go toolchain stamps the binary with the commit it was built from. `dev` appears only when there is no build information at all.

```
```

`main()` contains no logic. `run(args, stdout, stderr)` returns the exit code, so tests call it in-process with in-memory buffers instead of starting a subprocess.

Output discipline: requested output (help, version) goes to stdout, and every diagnostic goes to stderr. This matters because `regreen mcp` will speak the MCP protocol over stdio, where stdout is reserved for the protocol and one stray print breaks the server.

Exit codes: `0` success, `1` error, `2` usage error (no command, or an unknown one).

## Planned layout

| Package | Responsibility | Milestone |
|---|---|---|
| `cmd/regreen/` | Entry point and subcommand wiring | M0 |
| `internal/config/` | Repo config (`regreen.yml`) and user config: loading and validation | M1 |
| `internal/policy/` | The policy engine. Pure functions, no I/O: takes a diff and a rule set, returns a verdict with reasons | M1 |
| `internal/failure/` | The normalized failure model | M2 |
| `internal/ci/` | The `CIProvider` interface | M2 |
| `internal/ci/github/` | The GitHub Actions adapter | M2 |
| `internal/vcs/` | Git operations: diff, commit, push, trailers | M3 |
| `internal/state/` | Local state (claimed commits), stored outside the repo | M3 |
| `internal/mcpserver/` | The MCP tools, a thin layer over the core | M3 |
| `internal/watch/` | Background watcher | M6 |
| `presets/` | YAML presets, embedded with `go:embed` | M5 |

## Planned flow

1. The developer or their agent pushes a commit.
2. The agent calls `wait_for_ci`. regreen asks the CI provider for the result of that commit.
3. On failure, the agent calls `get_failure` and receives a normalized, trimmed failure. Log text is untrusted data and is never executed.
4. The agent calls `apply_autofix`. If the project's own fix command resolves the failure, the deterministic change is committed on its own.
5. If errors remain, the agent edits files and calls `submit_fix`. regreen reads the diff, runs the policy engine, runs every configured check, and only then commits and pushes.
6. In CI, `regreen verify` applies the same policy, reading it from the base branch. Branch protection makes that check required.

## Trust model

The fixing agent is untrusted. regreen believes the git diff and the result of re-running the checks, and nothing the agent says about its own work. Local protections (the MCP tool flow, the pre-push hook) catch problems early; the enforcement that cannot be bypassed is the CI check plus branch protection, because the agent cannot edit either.

Always-protected paths, hardcoded and not configurable: `regreen.yml`, `.github/**`, `.regreen/**`, and git hooks.

- **Decision:** Apache-2.0.
- **Alternatives:** MIT.
- **Why:** Chosen by the maintainer. Permissive like MIT, with an explicit patent grant.

## D2. Module path: `github.com/Tawfiq-alqaidy/regreen-ci`

- **Date:** 2026-11-23 (M0)
- **Decision:** The module path matches the git remote exactly, including case.
- **Alternatives:** A lowercased owner name.
- **Why:** Chosen by the maintainer. `go install github.com/Tawfiq-alqaidy/regreen-ci/cmd/regreen@latest` works without a redirect.

## D3. Minimum Go version: latest stable only (<GO_VERSION>)

- **Date:** 2026-11-23 (M0)
- **Decision:** Support only the current stable Go release. The `go` directive in `go.mod` is the single source of the version; CI reads it with `go-version-file`.
- **Alternatives:** Supporting the latest two releases, as Go's own support policy does.
- **Why:** Chosen by the maintainer. A new project has no users on older toolchains, and one version keeps CI simple.

## D4. CLI on the standard library, no CLI framework

- **Date:** 2026-11-23 (M0)
- **Decision:** Dispatch subcommands with a plain `switch` in `run`. No cobra, urfave/cli, or kong.
- **Alternatives:** cobra (the most common Go CLI framework).
- **Why:** The brief asks for few dependencies, each justified. regreen has a handful of subcommands with few flags, which the standard library handles. If flag handling grows past what `flag.FlagSet` per subcommand does comfortably, revisit this.
- **Cost if wrong:** Moving to cobra later means rewriting `cmd/regreen/app.go` and its tests; nothing under `internal/` depends on it.

## D5. `run(args, stdout, stderr) int` instead of logic in `main()`

- **Date:** 2026-11-23 (M0)
- **Decision:** `main()` only calls `run` and exits with its return value. `run` receives its output streams as parameters.
- **Alternatives:** Logic in `main()` tested by building and executing the binary.
- **Why:** In-process tests are fast and can assert exactly what goes to stdout and what goes to stderr. That separation is a hard requirement for `regreen mcp`, where stdout carries the protocol.

## D6. Version from ldflags, then Go build info

- **Date:** 2026-11-23 (M0)
- **Decision:** `regreen version` reports the value injected with `-ldflags "-X main.version=..."`, else the module version from `runtime/debug.ReadBuildInfo`, else `dev`. The build-info version is the release tag for `go install module@version`, and a pseudo-version naming the commit (for example `v0.0.0-<date>-<commit>+dirty`) for a local `go build` in a git checkout.
- **Alternatives:** ldflags only; build info only.
- **Why:** Release builds control the string through ldflags, and users who install with `go install` still see a real version without any release tooling. Local builds are left with the toolchain's pseudo-version instead of being forced to `dev`, because it says exactly which commit the binary came from and whether the tree was modified.

## D7. Linting with golangci-lint <GOLANGCI_LINT_VERSION>

- **Date:** 2026-11-23 (M0)
- **Decision:** golangci-lint v2 with the `standard` linter set plus errorlint, gocritic, gosec, misspell, revive, unconvert, and unparam; gofmt and goimports as formatters. The version is pinned in the `Makefile` and repeated in `.github/workflows/ci.yml`; the two must be changed together.
- **Alternatives:** `go vet` and `staticcheck` run separately; an unpinned "latest" linter.
- **Why:** One tool, one config file, the same result locally and in CI. Pinning stops a new linter release from failing CI on an unrelated commit. gosec is included because regreen runs commands and handles tokens. The linter is a development tool run with `go run`, not a dependency in `go.mod`.

## D8. GitHub Actions pinned to commit SHAs

- **Date:** 2026-11-23 (M0)
- **Decision:** Every `uses:` in the workflow references a full commit SHA with the tag in a trailing comment. The workflow's token is limited to `contents: read`.
- **Alternatives:** Pinning to a major tag such as `@v4`.
- **Why:** Tags can be moved; a SHA cannot. regreen is a tool about not weakening CI, so its own CI should not be changeable from outside the repository.
