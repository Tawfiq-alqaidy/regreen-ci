# Milestone M1: Config loading and the policy engine

A plain-language summary for a maintainer who wants to understand every part and may be new to Go.

## What was built

- `internal/policy`: the policy engine. It has no I/O and uses only the Go standard library. It holds the rules, the always-protected paths, a matcher for path patterns, a parser that turns `git diff` output into a data structure, and `Evaluate`, which decides whether a diff is allowed.
- `internal/config`: loads `regreen.yml` (the repository's checks and policy) and the per-user config, validates them strictly, and turns the policy part into a `policy.Rules` value.
- One dependency, `go.yaml.in/yaml/v4` v4.0.0, used only by `internal/config` (decision D11).
- Tests, including real patches produced by git for the hardening scenarios, and a fuzz test for the parser.
- Documentation: a new [configuration reference](../CONFIG.md), an updated [architecture](../ARCHITECTURE.md), decisions D11 to D30, and this file.

**Nothing calls these packages from the command line yet.** `regreen` still prints help and its version and nothing else. The packages are tested libraries waiting for M3 (the MCP server) and M4 (`regreen verify`).

## How the pieces connect

```
regreen.yml bytes --config.ParseRepo--> Repo{Checks, Policy policy.Rules}
patch text        --policy.ParseUnifiedDiff--> policy.Diff
policy.Input{Diff, Rules, ErrorFiles, AttemptsUsed} --policy.Evaluate--> policy.Verdict
```

Files in `internal/policy/`:

- `diff.go`: the data model. A `Diff` is a list of `FileChange` values; each has a path, a kind (modified, added or deleted), the lines it adds (with their line numbers in the new file), how many lines it deletes, and flags for binary and special changes.
- `glob.go`: the pattern matcher for `protected_files`. `ValidatePattern` and `MatchPath` share one parsing function, so a pattern the validator accepts is a pattern the matcher understands. `MatchPath` fills a small table (pattern segments by path segments), so its cost grows with the product of the two lengths, never exponentially, whatever path the agent picks.
- `paths.go`: `checkRepoPath`, the one path check the parser and `Evaluate` both use: clean and repo-relative, valid UTF-8, no control characters, at most 4096 bytes and 255 segments.
- `protected.go`: the always-protected list, and `IsProtected`, which checks a path against that list and a config's extra patterns.
- `parse.go`: `ParseUnifiedDiff`. It reads the output of one exact `git diff` invocation and returns an error for anything it does not recognize.
- `policy.go`: `Rules`, `Input`, `Verdict`, `Reason`, the rule names, and `Evaluate`.

Files in `internal/config/`:

- `repo.go`: `ParseRepo` (bytes in, validated `Repo` out) and `LoadRepo` (reads a file, then calls the same code), plus the shared strict decoder.
- `user.go`: `LoadUser`, `UserConfigPath`, and the defaults for the user config.

`Evaluate` takes the diff, the rules, the files named in the failure's errors, and the number of attempts already used. It takes nothing the agent says about its own work. It returns every reason it finds, not just the first. If the rules themselves are invalid it returns only those reasons. Otherwise it checks attempts and an empty diff, then each file (path, malformed entry, protected path, edit scope, binary, special, forbidden patterns), then the totals (deleted lines, changed lines). The diff is allowed exactly when there are no reasons. The exact order is in [the architecture document](../ARCHITECTURE.md), and the meaning of each rule is in [the configuration reference](../CONFIG.md).

To call the packages yourself, make a scratch test file, for example `internal/scratch/example_test.go` (delete it when you are done; do not commit it). It parses a `regreen.yml`, parses a patch, and evaluates it. The patch is the real output of `git -c core.quotepath=off diff --no-color --no-ext-diff --no-textconv --no-renames --ignore-submodules=none` for a change that adds a lint-suppression comment.

```go
package scratch

import (
	"fmt"
	"testing"

	"github.com/Tawfiq-alqaidy/regreen-ci/internal/config"
	"github.com/Tawfiq-alqaidy/regreen-ci/internal/policy"
)

const regreenYML = `
checks:
  - name: lint
    run: npx eslint .
policy:
  forbidden_patterns:
    - eslint-disable
`

const patch = `diff --git a/src/a.ts b/src/a.ts
index a91d231..595e119 100644
--- a/src/a.ts
+++ b/src/a.ts
@@ -1,4 +1,5 @@
 const a = 1;
-const b = 2;
+// eslint-disable-next-line no-unused-vars
+const b = 22;
 const c = 3;
 const d = 4;
`

func TestTryIt(t *testing.T) {
	repo, err := config.ParseRepo([]byte(regreenYML))
	if err != nil {
		t.Fatal(err)
	}
	diff, err := policy.ParseUnifiedDiff(patch)
	if err != nil {
		t.Fatal(err)
	}
	verdict := policy.Evaluate(policy.Input{
		Diff:         diff,
		Rules:        repo.Policy,
		ErrorFiles:   []string{"src/a.ts"},
		AttemptsUsed: 0,
	})
	fmt.Println("allowed:", verdict.Allowed, "attempts remaining:", verdict.AttemptsRemaining)
	for _, r := range verdict.Reasons {
		fmt.Printf("%s %s:%d %s\n", r.Rule, r.File, r.Line, r.Message)
	}
}
```

Run it:

```sh
go test ./internal/scratch -run TestTryIt -v -count=1
```

Expected output:

```
=== RUN   TestTryIt
allowed: false attempts remaining: 2
forbidden_pattern src/a.ts:2 added line contains forbidden pattern "eslint-disable"
--- PASS: TestTryIt (0.00s)
PASS
ok  	github.com/Tawfiq-alqaidy/regreen-ci/internal/scratch	0.688s
```

Things to try, each checked: replace `eslint-disable` with `eslint-OFF` in the patch only (leave the YAML alone) and the verdict is `allowed: true`, because the pattern no longer matches the added line; change `ErrorFiles` to `[]string{"src/other.ts"}` and an `edit_scope` reason appears before the `forbidden_pattern` one; set `AttemptsUsed: 2` and a `max_attempts` reason appears first. (The test passes in every case; it only prints the verdict.)


## Go idioms used and why

**A pure package with injected inputs.** `internal/policy` does no I/O: it cannot read files, the environment or the clock, and cannot call another program. Everything `Evaluate` knows arrives as an argument, so calling it twice with the same input gives the same answer, and a test needs no temporary files. The rule is enforced, not just intended: `TestPolicyPackageIsPure` uses the standard library's `go/parser` to read the import lists of the package's source files and fails if one imports anything not on a short allowlist of standard-library packages (`errors`, `fmt`, `path`, `slices`, `strconv`, `strings`, `unicode/utf8`). An allowlist rather than a list of banned packages means a new import has to be added to the test on purpose. It parses the files without compiling them (`ImportsOnly`), which is the cheap way to ask "what does this file import?"

**Table-driven tests and subtests.** A test is a slice of structs (a name, an input, the expected result) and a loop that runs each with `t.Run(name, ...)`. Adding a case is adding one line, and a failure names the case that broke. `TestMatchPath`, `TestEvaluate` and `TestParseUnifiedDiff` are built this way. Some, such as `TestMatchPath`, call `t.Parallel()` so their cases run concurrently.

**`errors.Join` and `%w`, with `errors.Is`.** `fmt.Errorf("...: %w", err)` wraps an error and keeps the original inside, so a caller can ask `errors.Is(err, fs.ErrNotExist)` however many layers of context were added. `LoadUser` uses this to treat a missing file as "use the defaults" rather than a failure. `errors.Join(problems...)` combines several errors into one, which is how a config with five mistakes reports all five. The strict decoder also compares against two sentinel values with `errors.Is`: `io.EOF` (the file had no document) and a package-private `errEmptyDocument`.

**Pointer fields to tell "omitted" from zero.** In the raw structs the numeric limits are `*int`, not `int`. A plain `int` is `0` whether the file says `max_attempts: 0` or says nothing, and those mean different things: the first is an error, the second means "use the default of 2". A `*int` is `nil` when the key is absent. (The raw struct's string keys use `yaml.Node` instead, which also lets the loader see whether a value was quoted; decision D23.)

**Returning a copy of a package-level slice.** The always-protected list is a package-level slice. `AlwaysProtected()` returns `slices.Clone(alwaysProtected)`, because a slice shares its backing array with its copies: a caller that sorted or edited the returned slice would otherwise change the list `Evaluate` uses. `TestAlwaysProtectedReturnsCopy` checks that.

**Typed string constants as enums.** `type EditScope string`, with constants `ScopeFilesInErrors` and `ScopeAny`, makes the set of valid values visible in code and lets the compiler tell an `EditScope` from any other string. Go has no enum keyword; this is the usual idiom. The same is used for `Delivery` in the user config. `ChangeKind` is an integer built with `iota` and has a `String()` method. The rule names (`RuleProtectedFile` and the others) are plain string constants, since they go into reasons that are shown to a person or an agent.

**Generics for one shared function.** `decodeStrict[T any]` decodes either a `rawRepo` or a `rawUser`, so both config files get the same strict rules (one document, unknown keys rejected, size cap) from one function instead of two copies.

**Native fuzzing.** `FuzzParseUnifiedDiff` is a Go fuzz test. `go test` runs it once on the seed inputs; `go test -fuzz` generates thousands of inputs per second and keeps the ones that reach new code. Its property is "whatever the parser accepts has a clean path without control characters, a non-negative deletion count and no newline inside an added line, and `Evaluate` judges it without panicking". A parser that reads untrusted text is the kind of code where inputs nobody thought of matter.

**`context.Context` as the first parameter.** `LoadRepo(ctx, path)` and `LoadUser(ctx, path)` do file I/O, so their first parameter is a context, as the Go convention says. At present each one only checks `ctx.Err()` before it starts; the file read itself cannot be cancelled. `ParseRepo` and the whole policy package take no context because they do no I/O.

## What the section 6 hardening table maps to

Section 6 of [the project brief](../superpowers/specs/regreen-ci-brief.md) lists eight scenarios. M1 covers the ones that need only a diff and a rule set. The test names below are real; the ones with `TestHardeningScenarios/` in front are subtests of the command shown above.

| Scenario | Covered in M1 by | Not covered in M1 |
|---|---|---|
| Agent runs `git push` directly | nothing | M4: `regreen init` (agent permission config), the pre-push hook, and `regreen verify`. M3's `submit_fix` is the only intended path to a push, but it does not exist yet. |
| Agent pushes with `--no-verify` | nothing | M4: `regreen verify` in CI, as a required check |
| Agent edits `regreen.yml` to relax rules | `TestHardeningScenarios/agent_edits_regreen.yml_to_relax_rules`: the always-protected path is rejected. `TestParseRepoDoesNotRemoveHardcodedProtection` (config package): a config cannot take it away. | M4: `regreen verify` reading the policy from the base branch. M1 only makes it possible, because `ParseRepo` takes bytes. |
| Agent removes the verify job from the workflow | `TestHardeningScenarios/agent_removes_the_verify_job_from_the_workflow` (subtests `delete_lines` and `delete_file`): `.github` is protected | M4: the documentation telling maintainers to make the check required in branch protection |
| Agent resets the attempt counter by deleting state | `TestHardeningScenarios/agent_resets_the_attempt_counter_by_deleting_state`: `Evaluate` takes attempts as a number, rejects when they run out, and a test pins the exact list of `Input` fields | M3: counting attempts from `Regreen-Fix` and `Regreen-Attempt` commit trailers |
| Agent passes lint by deleting or commenting out code | `TestHardeningScenarios/agent_passes_lint_by_deleting_code`, `.../agent_passes_lint_by_commenting_out_code` (both stopped by `max_deleted_lines`), `.../agent_passes_lint_with_a_suppression_comment` (forbidden patterns on added lines), `.../agent_edits_a_file_the_errors_do_not_name` (edit scope) | whether the fix is logically sound: the rules cannot see that, so it is left to human review |
| Fix for one check breaks another | nothing | M3: `submit_fix` runs every configured check before pushing |
| Instructions injected through CI logs | `TestHardeningScenarios/instructions_injected_through_CI_logs`: whatever the log said, the diff it produced touching `.github` and `.husky` is rejected | M2 and M3: trimming and delimiting log text, and never executing it |

Beyond the table, `TestHardeningScenarios` also checks that an honest one-line fix is allowed (`.../an_honest_one-line_fix_passes`), that a re-pointed symlink is rejected (`.../agent_re-points_an_existing_symlink`), that an edit adding `ignore = all` to `.gitmodules` (which would make git hide later submodule changes) is rejected as a protected file (`.../agent_hides_a_submodule_change_with_ignore_=_all_in_.gitmodules`), and that a patch the parser cannot read is an error, not an allowance (`.../unparseable_diff_is_not_evaluated`).

Three rows have no M1 coverage at all: running `git push` directly, `--no-verify`, and a fix for one check breaking another. They need code that does not exist yet. Three more (the `regreen.yml` edit, the workflow edit and the attempt counter) are covered only for the part that needs just a diff and rules; the rest is in the right-hand column.

## What is deliberately not here yet

- Any command that uses these packages. `regreen verify` and `regreen init` are M4; the MCP server (`regreen mcp`) is M3.
- Running git. The parser accepts text; the code that produces it with the right flags is `internal/vcs` in M3.
- Counting attempts from commit trailers (M3), and local state (M3).
- Extracting the files named in a CI failure's errors, which is what `edit_scope: files_in_errors` relies on (M2).
- The CI adapter and the failure model (M2).
- Reading the policy from the base branch (M4).
- Running the checks' `run` and `fix` commands. The config package stores them and never runs them.
- Using the user config (M6), and presets (M5).

## Known limitations

- **The engine guarantees that a fix follows the rules, not that it is correct.** A fix can pass every rule and still be wrong. Human review before merge is part of the design.
- **Literal forbidden patterns can be evaded by rewording.** `eslint-disable` does not catch another linter's alternative suppression syntax (`noqa`, `nolint`, `prettier-ignore`, `ignore_for_file` and so on, each needs its own entry), or text that has been rephrased. A pattern split across two added lines, or built at run time by concatenating strings, is not matched, because each line is checked on its own. Patterns are case-sensitive. This is why review stays part of the design (decision D14).
- **Limits count lines, not bytes.** One very long added line counts as one line against `max_changed_lines`.
- **Small deletions are allowed.** Deleting a failing test, or a small file the errors name, is allowed as long as it stays within `max_deleted_lines` and the edit scope. Adding or deleting an empty file changes no lines at all, so only the edit scope and the protected paths apply to it.
- **Path lists do not know about equivalent files.** Protecting `.eslintrc*` does not protect `eslint.config.js`, which configures the same tool. Each file that matters must be listed.
- **Only the end result is judged.** The engine sees the diff from the base tree to the head tree; intermediate commits on the way are not judged one by one.
- **`edit_scope: files_in_errors` trusts the list of files it is given.** The engine does not look at the CI errors; the caller extracts the names. That extraction is M2's job, and a wrong list there is a wrong scope here.
- **The parser needs an exact input.** It requires `git diff --no-renames --ignore-submodules=none` output with the flags in its comment, produced by following the git invocation checklist in [the architecture document](../ARCHITECTURE.md). Settings that change the format make the parser reject the output (decision D22). Some settings instead make git omit changes, such as submodule `ignore` settings in `.git/config` or `.gitmodules`; the parser cannot notice a change git never printed, so the M3 code that runs git must override them (decision D29).
- **Some harmless diffs are rejected.** A binary file, a changed file mode, a new executable file, a symlink or a submodule is a rejection by the engine. A path with a control character, non-UTF-8 bytes, more than 4096 bytes or more than 255 segments is a parse error. A file replaced by a symlink (git reports two sections for one path), a path containing a backslash, and a patch that contains rename lines are parse errors. A caller must treat a parse error as a rejection, never as an allowance.
- **Config is strict and can be inconvenient.** Unquoted `true` or numbers where text is expected, anchors, aliases and unknown keys are all errors.
- **Protected patterns from the config are case-sensitive**, while the built-in list is not. On a file system that ignores case, a config pattern `Tsconfig.json` does not protect `tsconfig.json`, and with `Makefile` protected, a diff that adds a new `makefile` is not stopped by that pattern (with `edit_scope: any`, or if the errors name it, it is allowed), although on such a checkout it can shadow or replace the protected file.
- **The always-protected list is a reading of the brief.** Hook tools not on the list are not covered until they are added (decision D16). `.gitmodules` goes beyond the brief's list (decision D26).
- **Nothing runs these packages outside tests.** All of the above is verified by tests, not by use.
