# Milestone M0: Scaffold

A plain-language summary for a maintainer who wants to understand every part and may be new to Go.

## What was built

- A Go module, `github.com/Tawfiq-alqaidy/regreen-ci`, with the Go version set by the `go` directive in `go.mod`.
- A small command-line program, `regreen`, in `cmd/regreen/`. It understands `help`, `version`, and four planned commands (`mcp`, `verify`, `init`, `watch`) that are listed in help but not built.
- A `Makefile` with `build`, `test`, `vet`, `lint`, and `check` targets.
- A golangci-lint configuration (`.golangci.yml`) and a GitHub Actions workflow (`.github/workflows/ci.yml`) that runs lint, vet, tests, and a build.
- Documentation: `README.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, and this file.

Nothing else works yet. There is no config loading, no policy engine, and no CI integration.

## How the pieces connect

There are three source files in `cmd/regreen/`, plus tests:

- `main.go` has `main()`. It calls `run(os.Args[1:], os.Stdout, os.Stderr)` and passes the returned number to `os.Exit`. It contains no other logic.
- `app.go` has `run()`, which looks at the first argument and decides what to do: print help, print the version, report a planned command as not built, or report an unknown command. It also holds the help text, the exit-code constants, the `plannedCommands` table, and the `readBuildInfo` variable.
- `version.go` has `resolveVersion()`, which chooses the version string: a value injected at build time, else the module version from the Go build information, else `dev`. An empty injected value counts as unset.

Exit codes: `0` success, `1` error (including a planned command that is not built), `2` usage error (no command, or an unknown one). Requested output (help, version) goes to stdout. Every diagnostic goes to stderr.

## How to try it by hand

From the repository root:

```sh
make build
```

This writes `bin/regreen`.

```sh
./bin/regreen help
```

Prints the help text to stdout and exits 0. The four planned commands are marked "(planned)". `./bin/regreen -h` and `./bin/regreen --help` do the same.

```sh
./bin/regreen
```

Prints the same help text to stderr and exits 2.

```sh
./bin/regreen version
```

Prints `regreen <version>` and exits 0. After a plain `make build` inside a git checkout the version is a pseudo-version such as `regreen v0.0.0-20261123191708-e17a0f4616c3`, or the same with `+dirty` appended if the working tree has uncommitted changes. The date and commit differ on every machine and commit. `./bin/regreen --version` does the same.

```sh
make build REGREEN_VERSION=v1.2.3
./bin/regreen version
```

Prints `regreen v1.2.3`.

```sh
./bin/regreen mcp; echo "exit $?"
```

Prints `regreen mcp: not implemented yet (planned for milestone M3)` to stderr, then `exit 1`. The other planned commands behave the same way: `verify` and `init` name M4, `watch` names M6.

```sh
./bin/regreen bogus; echo "exit $?"
```

Prints `regreen: unknown command "bogus"` and `Run 'regreen help' for usage.` to stderr, then `exit 2`.

To run the project's checks:

```sh
make check
```

This runs `go vet`, golangci-lint (downloaded and run through `go run`, so the first run is slow), and `go test -race ./...`. It exits 0 when everything passes.

## Go idioms used and why

**`run()` takes `io.Writer` parameters.** `run(args []string, stdout, stderr io.Writer) int` receives its inputs and outputs instead of reading `os.Args` and writing to `os.Stdout` itself. In production they are the real streams. In tests they are in-memory `bytes.Buffer` values, so a test can call `run` directly and check exactly what went to stdout and what went to stderr, without starting a subprocess.

**`os.Exit` only in `main`.** `os.Exit` ends the process immediately and skips deferred functions, and it cannot be tested in-process. Keeping it in the one-line `main()` means everything else returns a value that tests can inspect.

**`-ldflags "-X main.version=..."`.** The Go linker can overwrite the value of a package-level string variable at build time. `-X main.version=v1.2.3` sets the `version` variable in package `main`. This stamps a release version without editing source. The `Makefile` passes this flag only when `REGREEN_VERSION` is set. The variable can only be set this way if it is a plain `var` of type `string`, which is why `version` is not a constant.

**`debug.ReadBuildInfo` and VCS stamping.** Since Go 1.18 the toolchain embeds build information in every binary, readable with `runtime/debug.ReadBuildInfo()`. `Main.Version` is the release tag for a binary installed with `go install module@version`. For a plain `go build` inside a git checkout, the toolchain stamps the version with the VCS state, producing a pseudo-version of the form `v0.0.0-<date>-<commit>` with `+dirty` appended when the tree has uncommitted changes. When there is no usable information (none, an empty version, or `(devel)`), regreen reports `dev`. See decision D6.

**Table-driven tests with `t.Run`.** Each test is a slice of structs (name, input, expected output), and a loop runs each one with `t.Run(tt.name, ...)`. Adding a case is adding one line, and a failure names the case that broke. `TestRun` and `TestResolveVersion` use this shape.

**`_, _ =` to discard a write error on purpose.** `fmt.Fprint` returns a byte count and an error. Linters flag silently ignored errors. Writing `_, _ = fmt.Fprint(...)` says the discard is deliberate. Here there is nowhere left to report a failed write to stdout or stderr.

**A package-level function variable swapped in tests.** `app.go` declares `var readBuildInfo = debug.ReadBuildInfo`. `run` calls the variable. `TestRun` replaces it with a fake that reports no build information and restores the original with `t.Cleanup`, so the expected output `regreen dev` does not depend on how the toolchain stamps the test binary. Tests that replace it must not run in parallel with each other. `resolveVersion` takes the same function as a parameter, which is the other way to make code testable and is what `TestResolveVersion` uses.

**`go run tool@version` to pin a dev tool.** The `Makefile` runs `go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0`. Go downloads and runs exactly that version, and the tool does not appear in `go.mod`, so it is not a dependency of regreen. The version is written in the `Makefile` and repeated in the CI workflow, and the two must be changed together (decision D7).

## What is deliberately not here yet

- M1: config loading (`regreen.yml`) and the policy engine.
- M2: the GitHub Actions adapter and the normalized failure model.
- M3: the MCP server (`regreen mcp`), local state, commit trailers, and worktree handling.
- M4: `regreen verify`, `regreen init`, the pre-push hook, and branch-protection documentation.
- M5: presets for JavaScript/TypeScript, Laravel, and Flutter.
- M6: the watcher (`regreen watch`).

The trust model in `docs/ARCHITECTURE.md` is a design for M1 to M4. None of it exists yet.

## Known limitations

- `run()` looks only at `args[0]`. Extra arguments are ignored, so `regreen version extra` prints the version and exits 0, and `regreen verify extra` reports the planned-command message. This stays until subcommands get their own flag parsing.
- Help and the command table are separate. A test checks that every planned command appears in the help text, but the help text and the table are still edited by hand.
- The version can be a long pseudo-version for local builds. This is intended (it names the exact commit) but is not a release version.
